# Idempotency Architecture

Status: **Phase 1 — Proposed**

How a re-run becomes safe: the `sba_instance_id` golden key, exactly-once semantics, the
per-resource "create or adopt" rule, the run-state state machine, compensating cleanup, and
reconciliation.

Related: [architectural-decisions.md §3 ](idempotency.md#3-guarantees),
[configuration-resolution.md](configuration-resolution.md),
[request-lifecycle.md](request-lifecycle.md), [failure-and-retry.md](failure-and-retry.md).

---

## 1. Why This Is a First-Class Concern

§22 is explicit that the platform must be safe to re-run and that idempotency keys must be
deterministic. The reason is not tidiness. In a multi-cloud platform running in production, a
re-run is the normal response to a failure, and a re-run that duplicates infrastructure is
worse than the original failure — it produces an unmanaged server that nobody knows to
decommission.

Three specific hazards:

| Hazard | Consequence |
|---|---|
| A second VM with the same name | A Windows host, a DNS record and a CMDB CI all collide; some of them "succeed" |
| A second DNS record for one FQDN | Round-robin to a half-built server |
| A second CMDB record for one `sba_instance_id` | Inventory and cost attribution both become unreliable, permanently |

The last one is the worst, because it is a data-quality problem that outlives the build and is
invisible to everyone who does not specifically look for it.

The design answer: **the key is a caller-generated UUID, assigned once, before any resource
exists, and the create-or-adopt decision is made against infrastructure that was tagged with
it at creation time.** The tag is the durable proof of ownership; the UUID is the stable
identity. Everything else follows from those two.

## 2. The `sba_instance_id` Golden Key

### 2.1 Definition

[AD-05](architectural-decisions.md#ad-05-sba_instance_id-is-the-golden-join-key):
a UUIDv4 generated by ServiceNow when the RITM is approved, carried unchanged through the
contract, the run context, every cloud tag, the ServiceNow record, the DNS record set, and the
CMDB record.

```
  ServiceNow RITM
        │  sys_id
        ▼
  sba_instance_id  (UUIDv4, generated once)
        │
        ├──▶ run_context.json          (per run)
        ├──▶ Azure   : tags / resource tags   + resource group name suffix
        ├──▶ AWS     : tags                    + Name tag value
        ├──▶ GCP     : labels                  + instance name
        ├──▶ ServiceNow : u_sba_instance_id on the CI record
        ├──▶ DNS     : the record set's owning key
        └──▶ CMDB    : the correlation ID
```

**Not derived, ever.** Not from a hash of the parameters, not from a name, not from a counter,
not from a timestamp. Those all collide eventually — a re-issued request for a deleted server
must not inherit the old key and adopt a stale resource.

### 2.2 Properties

| Property | Value | Why |
|---|---|---|
| Format | UUIDv4, lowercase, hyphenated | Fixed length; no information; no collision |
| Assigned | Once, at approval | Before any resource exists, so it can be the ownership key |
| Cardinality | One per requested server | `count: 4` ⇒ four keys |
| Visible | In the contract and in every sink | Enables a leak test ([cicd-pipeline.md §4.4 ](cicd-pipeline.md#44-test)) |
| Mutable? | **Never** | A mutated key orphans the resource it identifies |

**One key per server, not per request.** This is the detail that makes reconciliation
tractable. A request-level key would let a four-server batch be identified as a unit but not
its individual members, and post-provision remediation is inherently per-server.

### 2.3 Idempotency key versus golden key

They are related, and conflating them is a mistake:

| | `sba_instance_id` | Idempotency key |
|---|---|---|
| Scope | One requested server | One execution attempt of one stage |
| Cardinality | 1 per server, forever | 1 per stage per run |
| Assigned by | ServiceNow, at approval | The engine, at dispatch |
| Value | UUIDv4 | `sba_instance_id` + `:` + stage + `:` + attempt |
| Purpose | Identity and ownership | Duplicate-suppression of a *request* |

The composite form follows directly from the golden key: the same server, same stage, same
attempt, asked twice, is the same logical request. Including `attempt` is what allows a
deliberate retry to actually do something, rather than being suppressed as a duplicate of the
attempt that just failed.

## 3. Guarantees

Six guarantees, in increasing order of how much they matter. "Exactly once" is not among them,
and that is deliberate.

| # | Guarantee | Statement |
|---|---|---|
| G-1 | **At-least-once dispatch** | The engine may attempt a stage more than once. It will never attempt it fewer times than once |
| G-2 | **At-most-one active run per instance** | [AD-21](architectural-decisions.md#ad-21-single-active-engine-per-run): a semaphore keyed on `sba_instance_id` |
| G-3 | **No duplicate infrastructure** | Re-running any stage never creates a second instance for the same `sba_instance_id` |
| G-4 | **Eventual convergence** | Re-running a stage moves the target to the desired state; it does not accumulate drift |
| G-5 | **Convergent under partial failure** | If a stage is interrupted, the next attempt completes it rather than restarting it |
| G-6 | **Ownership is provable** | Any resource the platform created is identifiable by its `sba_instance_id` |

### 3.1 Why not exactly-once

Distributed systems do not provide exactly-once side effects, and a design that claims
otherwise is describing something it cannot deliver. The realistic combination is:

```
  at-least-once execution  +  idempotent operations  +  a single source of truth
       (G-1)                     (G-3, G-4)              (G-5, G-6)
```

**The false-failure case is the reason this matters.** A cloud provider may return a timeout
for a create call that in fact succeeded. The platform cannot distinguish "it failed" from "it
succeeded and the response was lost". It must therefore:

1. record the intent in the run state *before* the call ("creating instance X"),
2. attempt the create,
3. on an ambiguous result, **read the world**: does a resource carrying `sba_instance_id`
   exist?
4. if yes, **adopt** it; if no, **create** it; if still not sure, retry the read, never the write.

An exactly-once claim would fail at step 3. A design that says "at-least-once plus
create-or-adopt" is both achievable and honest about where the uncertainty is.

## 4. Create-or-Adopt

The core mechanism. It is the same code on every provider, and it is what makes G-3 hold even
when the first attempt's response was lost.

```
  ┌─────────────────────────────┐
  │ 1. Read run state          │  attempt N recorded?
  └──────────────┬──────────────┘
                 ▼
  ┌─────────────────────────────┐
  │ 2. LOOK UP by sba_instance_id  ◀── the authoritative check
  │    (tag query, not by name)    │     NOT a name lookup
  └──────────────┬──────────────┘
                 ▼
        ┌────────────────┴────────────────┐
        │                                 │
   exactly one found                  none found
        │                                 │
        ▼                                 ▼
  ┌──────────────────┐           ┌──────────────────┐
  │ 3a. VERIFY       │           │ 3b. CREATE       │
  │   attributes     │           │   immediately     │
  │   vs. desired    │           │   with the tag    │
  └────────┬─────────┘           └────────┬─────────┘
           │                              │
           ▼                              ▼
  ┌──────────────────┐           ┌──────────────────┐
  │ 4a. CONVERGE     │           │ 4b. RECORD       │
  │   (idempotent    │           │   resource ids    │
  │   update only)   │           │   + the tag       │
  └──────────────────┘           └──────────────────┘
           └──────────────┬───────────────┘
                          ▼
                  ┌──────────────────┐
                  │ 5. Record stage  │
                  │    attempt OK    │
                  └──────────────────┘
```

### 4.1 Lookup by tag, never by name

```python
# Correct: ownership is proven by the tag
existing = cloud.list_instances(
    filter=[{"name": "sba_instance_id", "op": "eq", "value": instance_id}]
)

# Wrong: a name lookup cannot tell this run's resource from an unrelated one
existing = cloud.find_by_name(derived_name)
```

A name lookup is wrong for three separate reasons: the name was *derived* (so it can collide or
drift), it may have been taken by something else, and it cannot distinguish an adopted
pre-existing server from one this run created. The tag lookup answers the only question that
matters — *is this my resource?* — and the answer is trustworthy because the tag is applied
atomically with the create on every provider.

**Ambiguity is an error, not a coin flip.** If the tag query returns more than one match, the
stage fails with `AMBIGUOUS_RESOURCE`. Choosing one arbitrarily could make two concurrent
attempts converge on the same instance while believing they had separate ones, and guessing
wrong means mutating a resource the platform does not own.

### 4.2 Attributes to verify on adopt

| Attribute | If different |
|---|---|
| Subscription / project | `IMMUTABLE_MISMATCH` — terminate; the key is in the wrong tenant |
| Region / zone | `IMMUTABLE_MISMATCH` — terminate; the key is in the wrong region |
| VM size | Converge (resize) if permitted, else `IMMUTABLE_MISMATCH` |
| Image reference | `OS_VERSION_MISMATCH` — never silently change the image of a running server |
| OS disk size | Converge by expanding the disk (Azure resizing the OS disk requires a deallocate) |
| Network / subnet | `IMMUTABLE_MISMATCH` — a NIC cannot be moved between subnets |
| Tags / labels | Converge to the full desired set; `TAG_WRITE_INCOMPLETE` is never ignored |
| Deletion protection | Converge |

Immutable attributes terminate and re-create. Mutable ones converge. The distinction is
recorded per provider in [provider-abstraction.md](provider-abstraction.md), because "mutable"
is not a property of the platform but of the cloud API.

### 4.3 The tag-with-create rule

> **The `sba_instance_id` tag must be applied in the same API call that creates the resource.**

Not before (impossible), and not after (a crash in between loses ownership). This is why the
provider abstraction requires a "create with tags" operation on every resource it manages, and
why an implementation that creates and then tags is a design violation rather than a style
preference: it opens a window in which the platform has created a resource it cannot prove it
owns, and can only recover it by name.

### 4.4 What is never re-created

| Resource | On mismatch |
|---|---|
| Any resource with a valid `sba_instance_id` tag | Converge, or terminate per §4.2 |
| A resource **without** the tag | Never adopt; `RESOURCE_NOT_OWNED` |
| A resource with a different `sba_instance_id` | Never touch; it belongs to another run |

The middle row is the guard against adopting something the platform did not create, which is
the precondition for destroying somebody's production server.

## 5. The Run-State State Machine

Per stage. Exactly-once within a stage, at-least-once across stages.

```
   ┌────────┐
   │ QUEUED │◀──────────────────────────────────────┐
   └────┬───┘                                       │
        │ lock acquired (CAS)                       │
        ▼                                           │
   ┌────────┐                                       │
   │ RUNNING│──────────────┐                        │
   └──┬──┬──┘              │                        │
      │  │                 │ failure                 │
      │  │ ambiguous       ▼                        │
      │  │          ┌──────────┐                    │
      │  │          │ UNKNOWN  │  state?            │
      │  │          └────┬─────┘                    │
      │  │               │ determine by tag lookup  │
      │  │      ┌────────┴────────┐                 │
      │  │      ▼                 ▼                 │
      │  │  ┌──────────┐    ┌──────────┐            │
      │  │  │ APPLIED  │    │ FAILED   │            │
      │  │  └────┬─────┘    └────┬─────┘            │
      │  │       │               │ exhausted       │
      │  ▼       │               ▼                 │
   ┌──────┐      │          ┌──────────┐             │
   │VERIFIED│     │          │ EXHAUSTED│             │
   └────┬──┘      │          └────┬─────┘             │
        │         │               │                  │
        │ success │               │ force requeue ───┘
        │         │               │    (operator)      │
        └─────────┴───────────────┘
              recorded durably
```

| State | Meaning | May transition to |
|---|---|---|
| `QUEUED` | Not started; no lock held | `RUNNING` |
| `RUNNING` | Lock held; work in progress | `APPLIED`, `UNKNOWN`, `FAILED` |
| `UNKNOWN` | The call's outcome is not known (timeout, connection drop) | `APPLIED`, `FAILED` — **only after a tag lookup** |
| `APPLIED` | The desired state was reached | `VERIFIED` |
| `VERIFIED` | The stage completed and the stage assertion passed | terminal; next stage |
| `FAILED` | Attempt failed; retryable | `QUEUED` (new attempt) |
| `EXHAUSTED` | Retry budget consumed | `QUEUED` (operator force) |
| `SKIPPED` | Deliberately not run | terminal |
| `COMPENSATING` | Rolling back a partial create | `COMPENSATED` |
| `COMPENSATED` | Rollback complete | terminal |

**`UNKNOWN` is the state that makes the false-failure case safe.** Without it, an ambiguous
result would be recorded as `FAILED` and the retry would attempt a create that had already
succeeded — the exact duplication G-3 forbids. The transition out of `UNKNOWN` is not a retry
of the write; it is a read.

### 5.1 Write-ahead intent

The intent is recorded **before** the cloud call:

```json
{
  "stage": "provision",
  "attempt": 1,
  "phase": "CREATING",
  "target": {
    "sba_instance_id": "3f9c1e2a-7b4d-4c8e-9a1f-2d6b8e0c5a37",
    "name": "pypa001",
    "region": "westeurope"
  },
  "observed": null
}
```

Two reasons this ordering is mandatory:

1. **Crash recovery.** If the process dies after the write and before the create, the next
   attempt knows a create may be in flight. If it dies after the create and before the record,
   only the tag lookup can recover it — which works, but is slower and depends on the tag
   having been applied atomically (§4.3).
2. **Audit.** "We were about to create this, and then we stopped" is a materially different
   statement from "nothing happened". The first implies a resource may exist.

`observed` is the response, or the adoption record:

```json
{
  "phase": "APPLIED",
  "observed": {
    "provider": "azure",
    "vm_id": "/subscriptions/.../virtualMachines/pypa001",
    "nic_id": "/subscriptions/.../networkInterfaces/nic-pypa001",
    "os_disk_id": "/subscriptions/.../disks/osdisk-pypa001",
    "resource_group": "/subscriptions/.../resourceGroups/sba-payments-prod-app",
    "adopted": false,
    "tags_verified": true
  }
}
```

`adopted` and `tags_verified` are recorded because they are the evidence for G-3 and G-6. A
result that says a VM exists but not whether it was adopted is not auditable.

## 6. Locking

### 6.1 Mechanism

Compare-and-swap on the run-state store. No advisory locks, no lease-renewal daemons, no
dependencies on a specific store's lock API — a CAS on a versioned object works in S3, GCS,
Azure Blob, Vault KV, or Postgres, which matters because
[AD-04](architectural-decisions.md#ad-04-run-state-store-is-the-execution-source-of-truth) does not
require one particular backend.

```json
// Lock acquisition
{ "op": "cas", "key": "runs/<correlation_id>/locks/provision:3f9c1e2a-.../",
  "if_version": 3, "if_none_match": "*",
  "set": { "value": {"holder":"aap-prod-1","acquired":"2026-09-28T10:00:00Z","ttl":900} } }
// Succeeds only if the key does not exist, or exists with version 3
```

| Rule | Value | Reason |
|---|---|---|
| Key | `locks/<stage>:<sba_instance_id>` | Per server, per stage; two servers never block each other |
| Granularity | Stage × instance | Host-level locking would deadlock a serial batch |
| TTL | 15 minutes, refreshed every 5 | A crashed holder must not block a run forever |
| On expiry | The lock is taken over; the new holder re-reads state first | Stale-lock recovery is safe because state is write-ahead |
| Contention | The stage stays `QUEUED`; the run is not failed | Queueing is correct behaviour, not an error |
| Timeout waiting | The environment's concurrency wait, then `RESOURCE_LOCK_TIMEOUT` | A run that can never get the lock is a design problem worth surfacing |

### 6.2 Why a semaphore for G-2

[AD-21](architectural-decisions.md#ad-21-single-active-engine-per-run) requires that only one engine
acts on an instance at a time. A distributed semaphore keyed on `sba_instance_id` enforces it
across GitHub Actions and AAP simultaneously — which an in-process lock cannot.

This matters because a human can, quite reasonably, re-dispatch a stuck `dev` run on GitHub
while an `nonprod` run of the same RITM is still queued on AAP. Without a cross-engine
semaphore, both would proceed, and both would create-or-adopt the *same* instance — convergent,
actually, but with two engines racing on its tags and its configuration, and with a run-state
history that has interleaved entries from two sources. The semaphore makes the second one wait.

### 6.3 What is *not* locked

Run-state writes outside a locked stage are unconditional appends, with the state writer's own
CAS on the state object. A status update from a webhook and a stage completion can therefore
coexist. Only *mutations of infrastructure* are serialised, which is the only place where
serialisation is actually required.

## 7. Per-Stage Idempotency Contract

What each stage must guarantee, and what its stage assertion checks.

| Stage | Idempotency contract | Stage assertion |
|---|---|---|
| `validate` | Pure. No infrastructure touched. Re-running after a catalogue change produces a new result — the *only* stage where that is correct, because validation is supposed to reflect current data | The contract validates and a configuration is resolved |
| `policy_gate` | Pure, but the decision is cached by the catalogue digest. A re-run after a policy change must re-evaluate | The current policy is satisfied, and the recorded decision's digest matches |
| `provision` | Create-or-adopt by `sba_instance_id`; converge mutable attributes; terminate on an immutable mismatch | Exactly one instance carries the key, in the right region, with the right size, disk and image |
| `os_config` | Module-level idempotence; every state-ful task declares its `when` | Re-running produces no changes; a drift check confirms the baseline still holds |
| `validate_os` | Pure and read-only | The baseline assertion passes, and the assertion is a real check, not a hard-coded success |
| `domain_join` | Adopt an existing computer object; never re-join a joined host; reset the password only if the recorded one is absent | The object exists in the intended OU and the host can authenticate |
| `install_agents` | Declare state for the desired version; converge | The reported version equals the desired version on every host |
| `enroll_agents` | Converge enrolment state | The heartbeat is received and the platform reports the host as managed |
| `dns` | Update records owned by this run; never delete a record not created by this run; never change the target of a record that exists with a different address | The forward record resolves to the instance's IP, and the record set carries the key |
| `cmdb` | Upsert by `sba_instance_id`; report a duplicate as an error rather than resolving it | Exactly one CI record carries the key, with the correct CI, environment, and application |
| `destroy` | Delete only resources carrying the key; never delete a resource without it | No resource with the key remains, and the record set is gone |

Two of these deserve a note.

**`policy_gate` must re-evaluate, but must not flip mid-build.** A build approved under a policy
and then re-validated under a stricter policy 40 minutes later could be blocked after its
infrastructure exists, which is unresolvable and confusing. The rule: the decision is recorded
with the catalogue digest at the time of evaluation, the stage is skipped on re-run **only if
the digest is unchanged**, and if the digest changed the run is **failed with
`POLICY_CHANGED_MID_BUILD`** rather than silently re-judged. A human restarts it deliberately.

**`destroy` needs its own state.** A destroy that fails halfway must be resumable, and "resume"
must mean "delete what is left", not "start again". It is also the one stage where the absence
of the tag is a reason to *stop* rather than to proceed (§4.4).

## 8. Re-run Flows

### 8.1 Re-run the whole run

**Guard: the run state must be `RECONCILING` or terminal-failed.** A re-run of a `SUCCEEDED`
run is rejected (`RUN_ALREADY_SUCCEEDED`) — it would re-verify working infrastructure for no
reason, and the CMDB upsert would bump `last_verified` on records nobody asked about.

```yaml
stage: provision
action: rerun
  # create-or-adopt finds it, verifies it, converges it, records a new attempt
```

| Original outcome | Re-run behaviour |
|---|---|
| `provision` never ran | Creates |
| `provision` ran, later stage failed | Verifies, converges if needed, then continues |
| `provision` ran, `UNKNOWN` | Tag lookup, then adopt or create |
| `provision` ran, `COMPENSATING` | Finishes the compensation first, then the create |
| `provision` returned a lost response | Tag lookup finds it; **adopted** |

### 8.2 Re-run a single stage

The most common operational action, and the reason stage state is stored per stage rather than
only per run.

```yaml
# A different operator, days later, after fixing a firewall rule
stage: domain_join
action: rerun
force: true
approval_ref: CHG0044121
```

- Reads the run state for that stage
- Verifies the recorded tags still carry the same `sba_instance_id`
- Re-resolves configuration, because a catalogue change since the original run is likely
- If the resolved configuration would change anything from the run context, the run fails with
  `CONFIGURATION_DRIFT_IN_RUN` and requires a fresh run

That last rule is the most important thing in this section. A stage re-run resolves the
*current* catalogue, so it can legitimately want to do something different from what the run
originally intended. Allowing that mid-run turns a deterministic build into a sequence of
individually-correct decisions with no consistent overall outcome, and it means a build that
was approved against one configuration gets another one applied to it. Forward-fix and
[AD-16](architectural-decisions.md#ad-16-forward-fix-over-auto-destroy) are for *failures*;
a configuration change requires a *new* request.

### 8.3 Resume after a crash

Handled by write-ahead state, and the reasoning is in §5.1. In short:

| State found | Action |
|---|---|
| `QUEUED` | Start the stage |
| `RUNNING`, TTL live | The holder is alive; wait |
| `RUNNING`, TTL expired | Take over; re-read state; do the tag lookup for any `CREATING` phase |
| `CREATING` phase recorded | **Tag lookup before any write** |
| `APPLIED`, not `VERIFIED` | Run the stage assertion; do not re-mutate |
| `VERIFIED` | Skip; move to the next stage |

## 9. Reconciliation

Reconciliation is a *scheduled, read-only* verification pass, distinct from a re-run. This
distinction matters: a re-run is an action taken in response to a specific known failure, while
reconciliation discovers problems nobody knows about yet.

### 9.1 Frequency and scope

| Sweep | Scope | Trigger |
|---|---|---|
| Per-stage assertion | Just the current instance | Immediately after each stage |
| Immediate drift check | Just the current instance | At the end of `os_config` and `validate_os` |
| Nightly | All `SUCCEEDED` runs modified in the last 24 h, and all active runs | `schedule` |
| Weekly | The full estate | `schedule` |
| On demand | A named subset | An operator, post-change |

Every sweep is **read-only** except where explicitly stated. A reconciliation that mutates
infrastructure is a re-run wearing a different name, and it would change production state on a
schedule with no operator present.

### 9.2 Per-resource reconciliation

```python
def reconcile_instance(instance_id):
    desired = resolve_catalog(instance_id)          # current catalogue
    actual   = query_provider_by_tag(instance_id)   # live provider state

    if actual is None:
        -> DRIFT_MISSING           # the server is gone
    elif actual.region != desired.region:
        -> DRIFT_IMMUTABLE         # never auto-correct
    elif actual.size != desired.size:
        -> DRIFT_SIZE              # report; correction needs a change
    elif actual.image != desired.image:
        -> DRIFT_IMAGE             # never auto-correct
    elif set(actual.tags) != set(desired.tags):
        -> DRIFT_TAGS              # report; a retry can correct
    elif not heartbeat_within(desired.heartbeat_max):
        -> DRIFT_HEARTBEAT         # report
    else:
        -> HEALTHY
```

| Drift class | Auto-correct? | Why |
|---|:--:|---|
| `DRIFT_TAGS` | **Yes**, on the next run | Metadata only. No runtime impact. A retry is safe |
| `DRIFT_SIZE` | No | A resize deallocates the instance. That is a production impact requiring a change |
| `DRIFT_IMAGE` | No | Never. An OS change is a rebuild |
| `DRIFT_IMMUTABLE` | No | Structurally impossible |
| `DRIFT_MISSING` | No | Out of band. Someone deleted it, deliberately or not. **Never auto-recreate** — a deleted server is often a decommission, and recreating it can resurrect a decommissioned service into a DNS record and a CMDB |
| `DRIFT_HEARTBEAT` | No | The cause is unknown. A reboot in progress, a network change, or an agent failure all look identical |
| `DRIFT_CMDB_MISSING` | No | Never auto-register. A registration is an assertion that a human or a request made about a server, and re-asserting it automatically defeats the purpose of the inventory's accuracy |

`DRIFT_MISSING` is the one that most needs stating. "The server is gone" is the *normal* end
state of a decommission, and a platform that helpfully rebuilds it would resurrect decommissioned
infrastructure into DNS and the CMDB. A ticket to confirm, never an instance.

### 9.3 Daily orphan report

Catches resources that escaped ownership tracking. The check is a periodic **tag-based resource
sweep** in the production subscription, comparing live resource tags against the run-state
store.

```
  For each resource in the managed subscriptions:
      if it has no sba_instance_id tag:
          -> ORPHAN_UNTRACKED     (never in a tag-compliant estate)
      else if it has one not present in the run state:
          -> ORPHAN_STALE          (the run state is gone; the resource is not)
      else if it has a run in state CREATING older than 2h:
          -> ORPHAN_INTERRUPTED     (a crash left it behind)
```

| Class | Cause | Action |
|---|---|---|
| `ORPHAN_UNTRACKED` | Something created infrastructure without the tag — a hand-built VM, a console click, or a platform bug | **Investigate. This is a control failure**, because it means the estate contains resources the platform cannot reason about |
| `ORPHAN_STALE` | The run state was deleted, or the resource outlived its run | Reconcile; the tag is still valid evidence of ownership |
| `ORPHAN_INTERRUPTED` | A crash between create and record | Run `compensate` for that run; the tag makes the target unambiguous |

`ORPHAN_UNTRACKED` is on the daily report and is a page when the count is non-zero. Every other
orphan class is a digest item. The asymmetry is deliberate: the first one indicates the
"tag-with-create" rule has been violated somewhere, and it is the condition under which
create-or-adopt cannot be trusted, so it deserves a stronger response than a stale state object.

## 10. Compensating Actions

Compensation is the platform undoing a *partial* creation. It is not the same as
`lifecycle: destroy` ([failure-and-retry.md §7.2 ](failure-and-retry.md#72-destroy-is-a-separate-approved-operation)),
and the two are easy to confuse:

| | Compensation | `destroy` |
|---|---|---|
| Trigger | An interrupted *create* | An explicit, approved request |
| Scope | The incomplete object being created | Every resource for the instance |
| Ownership | The resource carrying this run's key | Every resource for the instance |
| Approval | None needed; it prevents orphaning | ServiceNow approval |
| Effect on a joined host | Never | Removes the AD object and the CMDB record |
| Authorization to delete | The resource this run created and recorded | The resources this run created |

### 10.1 Resource registration

The platform keeps a **local** record of what it created during the run, independent of
provider-side state. Provider state is a *cache*; this is the *record*.

```json
{
  "sba_instance_id": "3f9c1e2a-7b4d-4c8e-9a1f-2d6b8e0c5a37",
  "compensation_state": "REGISTERED",
  "resources": [
    { "kind": "vm",       "id": "...", "phase": "CREATED", "adopted": false },
    { "kind": "nic",      "id": "...", "phase": "CREATING", "adopted": false },
    { "kind": "os_disk",  "id": "...", "phase": "PENDING" }
  ]
}
```

| `compensation_state` | Meaning |
|---|---|
| `REGISTERED` | Resources are being created; a failure here triggers cleanup |
| `CLEANING` | Compensation is in progress |
| `COMPENSATED` | Everything that existed has been deleted |
| `RELEASED` | Creation completed; compensation is no longer permitted |

### 10.2 The rule

> **Compensation deletes only resources this run created (`adopted: false`).**
> **An adopted resource is never deleted by compensation.**

An adopted resource is a pre-existing server that this run took ownership of. If compensation
deleted it because a later step failed, the platform would have destroyed a production server
that existed before the request. Compensation runs exactly once, before the `RELEASED` state is
reached, and `RELEASED` is one-way: after the create completes, no automatic cleanup can touch
it, whatever happens later.

### 10.3 Ordering

Deletion runs in reverse creation order, because of the dependency edges:

```
  create:  vm  ->  nic  ->  os_disk
  delete:  os_disk  ->  nic  ->  vm
```

Deleting the VM first orphans its NIC and its managed disk, which then appear in the next day's
`ORPHAN_UNTRACKED` report. Reverse order plus the recorded ids means compensation is itself
idempotent, and a second compensation pass is a no-op.

## 11. Known Limitations

Stated rather than glossed over, because each has a mitigation that depends on operators
following a procedure.

| # | Limitation | Consequence | Mitigation |
|---|---|---|---|
| 1 | **Tag-based ownership depends on immutability** | If a tag can be changed by anyone, ownership is not enforceable | Tag-write permission is limited to the platform identities ([AD-12](architectural-decisions.md#ad-12-canonical-workflows-live-in-githubworkflows), [security-architecture.md §3.2 ](../security/security-architecture.md#32-cloud-permission-shape-example-azure)); `ORPHAN_UNTRACKED` is paged |
| 2 | **A mutable tag breaks create-or-adopt** | The lookup returns nothing, and the platform creates a duplicate | Change to a key attribute is a CI-gated, reviewed change ([cicd-pipeline.md §2.1 ](cicd-pipeline.md#21-what-each-stage-is-for-and-what-it-cannot-catch)); `I-8` invariant |
| 3 | **Detection of an externally deleted resource is delayed** | Up to the reconciliation interval | Nightly sweep + on-demand |
| 4 | **Reconciliation cannot fix immutable drift** | A drifted instance needs a change | `DRIFT_*` in the daily report; a change per correction |
| 5 | **A lost response is resolved by a read, which can itself be eventually consistent** | A very rare double-create | Retry the read with a bounded backoff before writing. If the read is still empty after that, a `PROVIDER_EVENTUAL_CONSISTENCY` error is raised rather than a write |
| 6 | **Two distinct requests may resolve to the same name** | A name collision | The `dns` stage is the backstop, and it is a *terminal* failure with a human — never an auto-resolve ([failure-and-retry.md §4.2 ](failure-and-retry.md#42-not-retryable--and-why)) |
| 7 | **A stage re-run resolves the current catalogue** | A mid-run configuration change | `CONFIGURATION_DRIFT_IN_RUN` → a new request is required |
| 8 | **A crashed holder's lock expires at the TTL** | A 15-minute window in which a stage is nominally "running" but is not | The takeover re-reads state and the write-ahead `CREATING` phase forces a tag lookup, so the window is safe, not merely unlikely |
| 9 | **The state store is a single logical dependency** | Its outage blocks the platform | `STATE_STORE_UNAVAILABLE` is retryable and then escalates as an availability incident ([failure-and-retry.md §10 ](failure-and-retry.md#10-escalation)); mutations stop rather than proceeding without durable state |
| 10 | **Compensation cannot always complete** | A resource survives a failed create | `ORPHAN_UNTRACKED`/`ORPHAN_STALE` in the daily report, with the tag as the recovery key |
